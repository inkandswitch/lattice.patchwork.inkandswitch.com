1. Why

Lattice can already estimate how big a piece of knitting will come out. size.js has Munden's loop constants, tightness and grams per square metre, and the Poincloux stretch model. loopsim.js lays loops out the way Shima Seiki's loop-simulation patents do. What it lacks is somewhere real to keep what's been measured. All of it is one fabric blob in one browser's localStorage, it describes one yarn for the whole machine, and no .k says which yarn went in which carrier.

The aim is to keep machines, yarns and the swatches knitted from them as shareable patchwork docs, and to let a .k point at them, so that the size estimate comes from real measurements and says where each number came from. The people working on them include someone with industry knitting experience (B Claxton), who should be able to open a profile, read it, correct it and comment on it without being walked through it.

What was said, and what's assumed

Said

  • Profiles for the machine and for each yarn, added to a project or account, and used by a given .k.
  • Kniterate at 7 gauge first. Other machines later, so a machine profile is real.
  • B will open profiles herself (aim for this), and chee will also enter things from conversation. Import of B's own sheets will come later.
  • Finished size, size across the piece, and the reverse (target size to needles) are all wanted. This spec covers the first.
  • A swatch from another Kniterate counts as measured, but is marked as such.

Assumed

  • "Account" means a folder of your own that the same docs are also linked into. No account-specific storage is needed.
  • Plain jersey and rib (1×1, 2×2) are sized. The first real swatch is a 2×2 rib. Interlock, tuck and the rest are recorded as "other" and only ever sized from a matching swatch.
  • One machine per .k.
  • Most early swatches won't have a .k, and some of what's known about them is believed rather than known.

2. Scope

The work was split into four specs, done in order:

  1. Profiles as docs (this spec): machine, yarn and swatch datatypes, their editors, and linking a .k to them.
  2. Finished size (this spec): the checks panel reads linked profiles and reports width × height and grams for each relaxation state, with where each number came from.
  3. Later: size across the piece, meaning width and height per row and an outline.
  4. Later: the reverse, from a target size to needles and rows at a stitch number, available to the .js.

Importing spreadsheets or spec sheets is out of scope until we've seen what B's look like.

3. The docs

Machine lattice:machine

{
  title: "the studio kniterate",
  make: "Kniterate", model: "Kniterate",
  gauge: 7,                 // needles per inch
  needles: 252,             // per bed
  beds: 2,
  carriers: ["1","2","3","4","5","6"],
  stitchSizes: {min: 0, max: 15},   // what the machine calls "stitch size", and its range
  stitches: {               // knitout's x-stitch-number → the machine's stitch size, per bed
    "5": {front: null, rear: null, note: ""}
  },
  floatLimit: 7,            // longest float, in needles (manual p.25: "6-7 stitches")
  notes: ""
}

The Kniterate manual (training copy) says stitch size is 0–15, set per row and separately for each bed (S/F, S/R, p.36). It gives no loop length for any number, so loop length is always measured on a swatch. Take-down (Roller, 0–999) and Speed (up to 800 mm/s) are also set per row, and both are recorded on swatches.

Two machines are the same model when make, model and gauge all match.

Yarn lattice:yarn

{
  title: "lambswool, oatmeal",
  fibres: [{fibre: "lambswool", percent: 100}],
  relaxesLike: "wool",       // wool | cotton | synthetic: which of Munden's tables applies
  count: {system: "Nm", value: 30, ply: 2},   // Nm | Ne | tex | denier
  supplier: "", colourway: "", colour: "#d8cbb0", lot: "",
  swatches: ["automerge:…"], // an index of the swatches that use it
  notes: ""
}

Tex is worked out, not stored: Nm gives 1000 × ply ÷ Nm, so Nm 2/30 is 66.7 tex; Ne gives 590.5 × ply ÷ Ne; denier gives denier × ply ÷ 9; tex gives value × ply.

Swatch lattice:swatch

{
  title: "lambswool 2×2 rib",
  knit: {
    machine: "automerge:…",
    feeds: [{carrier: "3", yarns: ["automerge:…", "automerge:…"], plated: true}],
    stitch: "5",             // knitout's x-stitch-number
    stitchSize: {front: null, rear: null},  // what the machine was set to, 0–15
    roller: null,            // take-down, 0–999
    speed: null,             // mm/s
    needles: null, rows: null, // needles: every needle in use, both beds together
    structure: "rib-2x2",    // jersey | rib-1x1 | rib-2x2 | other
    structureNote: "",       // what it is, for "other"
    k: null,                 // the .k that knit it, if there is one
    kHash: null,             // fingerprint of that .k when filled from it
    sure: "guessed",         // known | believed | guessed
    note: "freshly knit on the kniterate; needles, rows, stitch and plating to ask Agnes"
  },
  relaxed: {
    dry:  {entered: "mm",    width: 98, height: 142, grams: 9.1, date: "2026-11-07", by: "chee"},
    steamed: {entered: "per10", wales: 49, courses: 74, grams: null, date: "…", by: "B"},
    wet:  null,
    full: null
  },
  loop: {mm: null, date: null, by: null},   // mm of yarn per stitch, from unravelling 100 stitches
  photos: [],                               // links to image docs (see open questions)
  notes: ""
}

Each relaxation state keeps which pair was entered: millimetres over the swatch's needles and rows, or wales and courses per 10 cm. The other pair is always derived from it, so the two can't disagree, and the record shows what was actually measured. (The values in the example are made up.) For rib, "wales" means needles per 10 cm, both beds counted, so that 1×1 and 2×2 can be compared and a rib's width follows from its needle count the same way jersey's does. Conventions vary, and this is one to check with B. There are four states. Three match size.js's RELAXED: dry (off the machine, left to lie), wet (soaked, spun, dried flat) and full (washed hot and tumbled). The fourth is steamed, the Kniterate manual's own method (left at least 10 minutes, steamed, laid flat, measured in 10 cm, p.41), which is probably also how B works. There are no published constants for steaming, so steamed is measured only: never estimated from another state, and never used to estimate one.

A swatch's feeds[].yarns are in the order knitting hole, then plating slit. Plated, the first shows on the face and the second on the back (manual p.23).

The swatch is the source of truth for which yarns it used. When the swatch editor sets or changes its feeds, it adds the swatch to each yarn's swatches index and removes it from any it no longer uses. The resolver only trusts an index entry whose swatch links back to that yarn.

What a .k gains

{
  …,
  yarns: […],                // knitoutjs's: colours and plating, untouched
  profiles: {                // lattice's own
    machine: "automerge:…" | null,
    carriers: {"3": ["automerge:…", "automerge:…"]}   // knitting hole, then plating slit
  }
}

The links live in a key of lattice's own, profiles. yarns belongs to knitoutjs (knitoutjs/core/yarns.js), whose picker replaces a carrier's whole entry whenever its colour changes, so anything kept inside it would be lost. Whether a carrier is plated or held is still read from yarns[i].plated.

A project

Nothing new is stored on a project. If a .k has no profiles.machine and the project's folder holds exactly one machine doc, that machine is used. Adding profiles to a project means filing them in its folder. Adding them to your account means also filing them in a folder of your own.

4. From a .k to its profiles

The check runs in a worker, so it needs plain data. A new profiles.js on the main thread does the following:

  1. Loads the .k's machine: its profiles.machine link, or else the project's only machine doc, or else none (falling back to today's gauge setting).
  2. For each carrier in profiles.carriers, loads those yarn docs, then every swatch in their swatches indexes, then each of those swatches' machines.
  3. Flattens all of it into a resolved profile and hands that to the check alongside the settings it already receives:
{
  machine: {url, title, make, model, gauge, needles, carriers} | null,
  carriers: {
    "3": {
      yarns: [{url, title, tex, relaxesLike}, …],
      plated: true,
      tex: 133.3,            // the strands' tex, summed
      swatches: [{url, title, sure, machine: {url, make, model, gauge}, stitch,
                  needles, rows, feeds, relaxed, loop}, …]
    }
  },
  loading: false,
  missing: [{url, why: "not found" | "no access" | "loading"}]
}

It listens for changes on every doc it loaded. When any of them changes, the .k changes, or the project's folder changes, it resolves again and the check runs again. The resolved profile is also turned into the per-carrier yarns fabric that loopsim.js's sizer() already accepts, so the 3D view and the animation agree with the readout.

5. From profiles to a size

This is worked out in size.js, as pure functions, for each carrier, stitch number and structure the .k uses. (Today it's done per stitch number alone.)

Which structure a pass is

knitcheck.js already works out which bed each pass knits on, to find tubes. It also classifies each pass by the needles it knits:

  • jersey: one bed only. A tube is jersey too, going round.
  • 1×1 rib: both beds, alternating front and back one needle at a time. On the Kniterate, knitting both beds needs half racking (±0.5, manual p.9 and p.34), so rib passes come at a half rack.
  • 2×2 rib: both beds, alternating in twos.
  • other: anything else that knits on both beds in the same pass, such as other rib layouts or interlock-like patterns.

The classification is made per pass and carried through to the size, so that a rib cuff and a jersey body in the same .k are each sized from their own structure.

Tiers

The first tier that applies wins:

  1. measured A swatch on this machine with the same yarns, plated or held the same way, at the same stitch number, in the same structure. Its width over its needles and its height over its rows give wales and courses per 10 cm.
  2. measured · other machine As above, but on another machine of the same model and gauge. It's used as measured, and the readout names the machine it came from.
  3. from loop A measured loop length for these yarns at this stitch number (from a swatch on any machine). Then courses ≈ 100 × kc ÷ loop and wales ≈ 100 × kw ÷ loop. kc and kw are fitted from this yarn's swatches that have both a loop length and a measured size, on any machine, since Munden says relaxed loop shape doesn't depend on the machine. Failing that, Munden's published values for the yarn's relaxesLike are used. This is what constants() and stitchSize() do now, fed per yarn. Jersey only to begin with. Rib gets this tier once Knapton et al.'s 1968 rib constants (1×1, 2×2, wool) are confirmed from the paper and added to size.js, fitted per structure the same way: kc and kw from a yarn's rib swatches only feed rib. "Other" never gets it.
  4. guess Nothing measured. Jersey: one stitch per needle pitch wide, as the 3D view assumes now. Rib and other: the same, and the readout says plainly that relaxed rib comes out much narrower than that (measure a rib swatch).

When several swatches qualify at the same tier, they're averaged and all of them are listed.

Relaxation states

Every state is reported. A state that was measured on the matching swatch is used as is. Steamed appears only when it was measured. Any other state that wasn't measured is estimated from a measured one: loop length is held constant, and courses scale by the ratio of kc between the two states, wales by the ratio of kw, using the RELAXED table for wool and the FIBRES ratios otherwise. An estimated state is marked as estimated.

Plating and holding

A carrier's tex is the sum of its strands, and that's what tightness and grams use. The Kniterate manual recommends a plated pair come to Nm 6–8 together (about 125–167 tex), and the readout notes a pair outside that range. A swatch only matches knitting fed the same way: single, plated or held. The plated lambswool swatch won't count as measured for single-strand lambswool, though its loop length still feeds into lambswool's kc and kw.

Provenance

Every size in the result carries its sources. checkKnitout's size grows to:

size: {
  states: {
    dry:  {width: {mm, stitches}, length: {mm, rows}, around, grams, estimated: false},
    wet:  {…, estimated: true},
    full: {…, estimated: true}
  },
  sources: [{carrier: "3", stitch: "5", structure: "rib-2x2", tier: "measured" | "other-machine" | "loop" | "guess",
             swatches: [{url, title, sure, machine}], count}],
  on: …   // the stretched-round-a-body figure, as now
}

The limits that are currently fixed to the Kniterate in knitcheck.js (KNITERATE.needles, its carriers and the pitch) come from the resolved machine when there is one.

6. The interface

Making profiles

index.js registers lattice:machine, lattice:yarn and lattice:swatch as datatypes, each with a tool. Lattice adds machine, yarn and swatch to the latticework's + menu (project.js's latticeOptions().menu). Opening a new doc there files it in the project. Lattice's fileExtension gives each profile datatype an extension of its own (machine, yarn, swatch), so TOOLS opens each in its editor. (Nesting swatches under their yarn in the file tree would mean changing knitoutjs's latticework, so it's left for later.)

The editors

The editors are plain forms in the style of the checks panel. They're written to make sense to someone from industry: standard terms first, with plain words beside them.

Shown asMeans
wales / 10 cmstitches across (for rib: needles across, both beds)
structurejersey, 1×1 rib, 2×2 rib, or other (described)
courses / 10 cmrows up
loop lengthmm of yarn in one stitch
countNm, Ne, tex or denier, with ply (tex is shown, worked out)
tightness factor√tex ÷ loop length (cm)
g/m²fabric weight
  • Machine: make, model, gauge, needles, beds, carriers, and the stitch table (one row per stitch number: setting name, value, note).
  • Yarn: fibres, how it relaxes, count and ply (tex shown), supplier, colourway and colour, lot, notes. Below that, its swatches, each summarised in a line (2×2 rib · st 5 · plated · 48 × 100 · washed: 98 × 142 mm · guessed), and a new swatch with this yarn button.
  • Swatch:
    • How it was knit: machine, feeds, stitch number, needles, rows, structure, and the known / believed / guessed switch with its note. There's a fill from a .k picker that takes needles, rows, stitch number and feeds from a .k's check.
    • Measured: one row per relaxation state. Enter width and height in mm, or wales and courses per 10 cm; the other pair is shown greyed. Then grams, date and who.
    • Loop length, photos, notes.
    • How it was knit includes the stitch size on each bed (0–15), the roller and the speed. A match whose roller or speed differs from the .k's says so. Next to the needles and rows is the manual's hint: "a good size for a reliable tension swatch is 80 needles by 80 rows", bigger for rib, which pulls in.
    • What follows: tightness factor, g/m², and this swatch's kc and kw (when it has a loop length).

Comments come for free: the workspace's comment provider already watches any doc that's open.

Linking a .k

  • What's loaded: a section of the checks panel, above the readout. It has a machine choice (the project's machine docs, or no machine (7 gauge)), and one row for each carrier the .k uses, with a yarn choice per strand (one, or two when yarns[i] has two colours). The choices are the project's yarn docs, or a pasted link. The colours stay knitoutjs's, set in its picker as now.

The readout

In the checks panel, in place of the current "how big it comes out":

relaxedwidth × heightgrams
off the machine186 × 142 mm9.1 g
washed172 × 134 mm estimated9.1 g
washed hot & tumbled168 × 129 mm estimated9.1 g

Below that is one line per carrier, stitch number and structure, for example carrier 3, st 5, jersey: measured from lambswool jersey, st 5 (believed), on the studio kniterate. Where the estimate could be better, it says what to measure: no swatch at st 7: knit one, or measure its loop length. (The numbers above are only an illustration: a 51 × 100 jersey swatch at 186 × 142 mm off the machine, with the washed states scaled by Munden's kw and kc ratios. Washing shrinks wool both ways.)

7. What stays, and migrating

  • A .k with no profiles works exactly as now, from the localStorage fabric and gauge.
  • The old fabric box stays visible only in that case. It gains a make profiles from this button, which creates a yarn doc (fibre, tex as a tex count, strands as ply) and one swatch per stitch number entered (its across and up, as measured "off the machine", or whichever relaxation was set), files them in the project and links them to the open .k.
  • A .k with profiles on some carriers and not others sizes the unlinked carriers from the localStorage fabric.

8. When things go wrong

  • A linked doc won't load (not found, no access, still syncing): it goes into missing, that carrier drops to the next tier, and the readout says so (yarn profile not loaded: guessed). It never fails silently and never blocks the check.
  • Still loading: the readout shows loading profiles… with the previous numbers until they're resolved.
  • A yarn with no swatches is sized "from loop" if it has a loop length, otherwise "guess", and the readout says what would improve it.
  • A swatch filled from a .k whose code has since changed (its hash differs): the swatch shows a notice and keeps its values, because the physical swatch hasn't changed. A fill again button is there if the change was a correction.
  • Nonsense input (zero, negative, blank): treated as not measured, the way size.js's measured() does now.
  • Editing at the same time: every field is its own key, so you and B editing at once merge cleanly through automerge.
  • A feed that doesn't fit the machine (a carrier the machine hasn't got, more needles than its bed): shown as a warning on the swatch, and still saved.

9. Testing

  • Unit tests with node --test for size.js and the matching: each tier; jersey vs. 1×1 vs. 2×2 rib (a rib swatch never sizes jersey, and the reverse); rib without a swatch falling to guess with its warning; this machine vs. another of the same model vs. another model; single vs. plated vs. held; averaging several swatches; estimating a missing relaxation state; tex from each count system; entered mm vs. per 10 cm round-tripping. The repo's test script (currently echo ':))') runs them.
  • Structure detection in knitcheck.js: small knitout fixtures for jersey, a tube, 1×1 rib, 2×2 rib, and a rib cuff followed by a jersey body.
  • Resolution in profiles.js, with an injected find(url) over plain objects: the project's only machine; a missing doc; an index entry whose swatch doesn't link back; re-resolving on change.
  • The round trip: a .k for the lambswool 2×2 rib swatch, once it's measured, must predict exactly the swatch's measured size at its own stitch number. This is the first real end-to-end check.
  • By hand: the editors and the readout in the dev server, and then B, for whether they make sense to someone from industry.

11. Open questions

  • Nesting swatches under yarns in the file tree needs a hook in knitoutjs's latticework, so it's left for later.
  • Photos. We need to confirm how patchwork holds images (an image or file datatype, or a blob in the doc) before the swatch editor gets a photo field. If that turns out to be awkward, photos are dropped from the first cut.
  • Stitch number to stitch size. The manual settles what the setting is (stitch size 0–15, per bed). The vendored converter writes knitout's x-stitch-number (0–9, A–Z) straight into each needle's stitch-size slot (STIF/STIR). It defaults to stitch 5, transfer stitch 3, roller 100 and speed 100. So a stitch number names an entry in the Kniterate's own stitch table, and what that entry is set to (0–15) is the machine's. The machine profile records it per entry, and it's worth confirming with Agnes what the studio machine's table holds.
  • The lambswool swatch is a 2×2 rib, so the jersey code that was a candidate for it (needles 50 to 100, single bed) isn't how it was knit. Its needle count, rows, stitch number and whether it was plated are all to ask Agnes. Until then it's entered as guessed, and its relaxed measurements are still worth recording now, since they don't depend on any of that.
  • Rib constants. We need to confirm Knapton et al. 1968 (the wool rib paper) and take its 1×1 and 2×2 rib constants, per relaxation state, before rib gets the "from loop" tier. Until then rib is measured or guessed only.
  • Counting rib. Rib is recorded as needles per 10 cm with both beds counted. Industry often counts face wales only. We need to check which B expects, and show both if needed.
  • Terms. Whether B would rather see different words (cpc/wpc, "course density", a different name for each relaxation state) once she's looked at it.
